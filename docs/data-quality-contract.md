# قرارداد کیفیت، تازگی و قابلیت اتکای داده

## هدف

این سند قواعد مشترک ارزیابی داده را برای تمام منابع بازار، مشتقات، اقتصاد کلان، اخبار و شاخص‌های ریسک تعریف می‌کند.

این قرارداد فقط برای دریافت، اعتبارسنجی و تحلیل داده است و شامل هیچ مسیر معامله، سفارش‌گذاری یا اجرای خودکار نیست.

## ابعاد کیفیت

هر `NormalizedSnapshot` باید بتواند حداقل این ابعاد را گزارش کند:

- **Schema validity**: ساختار و نوع فیلدها معتبر است.
- **Completeness**: فیلدهای الزامی وجود دارند.
- **Temporal validity**: timestampها معتبر، قابل‌مقایسه و دارای timezone هستند.
- **Freshness**: فاصلهٔ زمان مشاهده تا زمان مصرف در محدودهٔ مجاز است.
- **Continuity**: در سری‌های زمانی، gap یا duplicate غیرمجاز وجود ندارد.
- **Consistency**: مقادیر با قواعد دامنه و منابع مرجع سازگارند.
- **Provenance**: منبع و reference داده قابل ردیابی است.

## Freshness policy

هر adapter باید آستانهٔ freshness خود را صریح اعلام کند. آستانه می‌تواند بر اساس نوع داده متفاوت باشد:

- دادهٔ لحظه‌ای بازار: آستانهٔ کوتاه و وابسته به interval؛
- OHLCV بسته‌شده: freshness بر اساس زمان بسته‌شدن کندل؛
- دادهٔ اقتصاد کلان: freshness بر اساس `published_at` و دورهٔ مرجع؛
- خبر: freshness بر اساس زمان انتشار و سیاست مصرف خبر؛
- شاخص‌های ریسک: freshness وابسته به تناوب انتشار provider.

اگر timestamp لازم وجود نداشته باشد، داده نباید به‌صورت معتبر علامت‌گذاری شود.

## وضعیت نتیجهٔ اعتبارسنجی

نتیجهٔ کیفیت باید یکی از وضعیت‌های قراردادی باشد:

- `VALID`
- `STALE`
- `INCOMPLETE`
- `GAPPED`
- `CONFLICTING`
- `INVALID`
- `UNAVAILABLE`

در صورت وجود چند مشکل، adapter باید مشکل اصلی را تعیین کند و جزئیات را در metadata خطا نگه دارد؛ نباید مشکل با مقدار پیش‌فرض یا دادهٔ ساختگی پنهان شود.

## قواعد مصرف

- فقط دادهٔ `VALID` می‌تواند بدون محدودیت وارد pipeline تحلیل شود.
- دادهٔ `STALE` یا `GAPPED` باید warning تولید کند و طبق policy ممکن است تصمیم را `BLOCKED` کند.
- دادهٔ `INCOMPLETE` یا `CONFLICTING` نیازمند policy صریح برای کاهش اعتماد یا توقف مصرف است.
- دادهٔ `INVALID` و `UNAVAILABLE` نباید به feature معتبر تبدیل شود.
- context اقتصاد کلان، اخبار و شاخص‌های ریسک نباید به‌تنهایی جهت `LONG` یا `SHORT` تولید کند.

## PIT و replay

- زمان دریافت (`received_at`) با زمان مشاهده یا انتشار (`observed_at`/`published_at`) متفاوت است.
- در replay، snapshot فقط زمانی قابل استفاده است که در زمان تصمیم در دسترس بوده باشد.
- اصلاحات تاریخی باید با version یا revision مستقل ثبت شوند.
- کندل بسته‌نشده باید صریحاً مشخص باشد و مصرف آن در featureهای نهایی ممنوع یا policy-controlled باشد.

## خطا، retry و rate limit

adapter باید خطاها را به دسته‌های قابل‌تشخیص تبدیل کند:

- خطای موقت شبکه؛
- timeout؛
- rate limit؛
- پاسخ نامعتبر؛
- احراز هویت یا پیکربندی نامعتبر؛
- نبود داده؛
- ناسازگاری schema.

retry فقط برای خطاهای موقت مجاز است و باید محدود، قابل مشاهده و deterministic باشد. خطاهای پیکربندی یا schema نباید با retry بی‌نهایت پوشانده شوند.

## حداقل خروجی audit

برای هر snapshot نامعتبر یا محدودشده باید قابل ثبت باشد:

- source و source kind؛
- instrument یا topic؛
- timestampهای موجود؛
- quality status؛
- دلیل یا کد خطا؛
- provenance؛
- schema version؛
- تصمیم مصرف‌کننده، مانند accept، warn، skip یا block.

## معیار پذیرش

- freshness و کیفیت برای هر adapter قابل مشاهده باشد؛
- دادهٔ نامعتبر یا قدیمی بی‌صدا وارد تصمیم نشود؛
- retry با خطاهای دائمی اشتباه نشود؛
- PIT و replay با timestampهای واقعی سازگار باشند؛
- contextهای غیرقیمتی مستقیماً جهت LONG/SHORT نسازند؛
- هیچ adapter به endpoint معاملاتی یا order execution متصل نباشد.
