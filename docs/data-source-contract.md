# قرارداد مشترک منابع داده

## هدف

این سند قرارداد پایهٔ تمام منابع اطلاعاتی پروژه را مشخص می‌کند؛ از providerهای بازار کریپتو تا منابع اقتصاد کلان، اخبار و شاخص‌های ریسک.

این قرارداد فقط برای **دریافت و تحلیل داده** است. هیچ منبع یا adapter نباید قابلیت ارسال سفارش، اجرای معامله یا دسترسی به endpointهای معاملاتی داشته باشد.

## مدل مفهومی

هر منبع باید داده را در سه لایه ارائه کند:

1. **Raw payload**: پاسخ خام provider، بدون تغییر معنایی.
2. **Normalized snapshot**: دادهٔ استانداردشده با schema مشترک.
3. **Analytical features/context**: ویژگی‌ها یا contextهای مشتق‌شده که provenance آن‌ها حفظ شده است.

## حداقل metadata هر snapshot

- `source`: نام پایدار provider یا منبع.
- `source_kind`: نوع منبع، مانند `exchange`, `aggregator`, `macro`, `news` یا `market_index`.
- `instrument` یا `topic`: دارایی/قرارداد یا موضوع مرتبط.
- `observed_at`: زمان مشاهدهٔ داده در provider، در صورت وجود.
- `published_at`: زمان انتشار داده، برای خبر و دادهٔ اقتصادی، در صورت وجود.
- `received_at`: زمان دریافت توسط سیستم.
- `effective_at`: زمانی که داده از نظر معنایی معتبر است، در صورت نیاز.
- `schema_version`: نسخهٔ قرارداد normalized.
- `quality`: وضعیت کیفیت داده.
- `provenance`: شناسه، URL یا reference قابل audit به منبع اصلی.

## وضعیت کیفیت داده

حداقل وضعیت‌های پیشنهادی:

- `VALID`: داده از نظر schema، زمان و freshness معتبر است.
- `STALE`: داده بیش از آستانهٔ مجاز قدیمی است.
- `INCOMPLETE`: بخشی از داده وجود ندارد.
- `GAPPED`: در سری زمانی gap تشخیص داده شده است.
- `CONFLICTING`: داده با منبع معتبر دیگر ناسازگار است.
- `INVALID`: schema یا مقدارها معتبر نیستند.
- `UNAVAILABLE`: provider پاسخ قابل‌استفاده نداده است.

داده‌های غیر `VALID` نباید بدون policy صریح وارد تصمیم شوند و ممکن است باعث warning یا `BLOCKED` شوند.

## قواعد زمانی و PIT

- `received_at` نباید جایگزین `observed_at` یا `published_at` شود.
- در replay تاریخی، فقط داده‌ای مجاز است که در زمان تصمیم در دسترس بوده باشد.
- revisionهای بعدی دادهٔ اقتصادی باید با نسخه و زمان انتشار جدید ثبت شوند.
- کندل بسته‌نشده باید صریحاً علامت‌گذاری شود و نباید به‌صورت پیش‌فرض وارد featureهای نهایی شود.
- timezone همهٔ timestampها باید مشخص و قابل تبدیل به UTC باشد.

## قواعد provider

هر adapter باید:

- فقط خواندنی باشد؛
- timeout، rate-limit و خطاهای شبکه را به خطای قراردادی تبدیل کند؛
- symbol، interval و نام فیلدها را normalize کند؛
- کیفیت و provenance را حفظ کند؛
- رفتار deterministic در برابر payload یکسان داشته باشد؛
- قابلیت fallback را از منطق تصمیم جدا نگه دارد.

## قواعد مصرف در تحلیل

- دادهٔ بازار می‌تواند feature تکنیکال تولید کند.
- دادهٔ مشتقات می‌تواند feature تأییدکننده یا ورودی risk evaluation باشد.
- دادهٔ اقتصاد کلان، اخبار و شاخص‌های کلان باید ابتدا به `MarketContext` یا `RiskContext` تبدیل شوند.
- منابع context نباید بدون قرارداد جداگانه مستقیماً LONG/SHORT تولید کنند.
- نبودن داده نباید با مقدار ساختگی یا default پنهان شود؛ مقدار ناموجود باید صریح باشد.

## ثبت و audit

برای هر تصمیم قابل audit باید امکان ردیابی این زنجیره وجود داشته باشد:

`source -> raw payload reference -> normalized snapshot -> feature/context -> decision`

حداقل باید source، زمان‌ها، schema version، quality و provenance قابل بازیابی باشند.

## معیار پذیرش

- قرارداد normalized برای همهٔ providerهای آینده قابل استفاده باشد.
- دادهٔ stale، ناقص، متناقض یا نامعتبر قابل تشخیص باشد.
- replay و PIT با metadata زمانی امکان‌پذیر باشد.
- منابع context از تولید مستقیم جهت معامله جدا باشند.
- هیچ مسیر دریافت داده‌ای به order execution یا trading endpoint متصل نباشد.
